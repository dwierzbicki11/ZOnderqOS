# SMT Stage 22 — final SMP stress and stability

Stage 22 is the final gate for the SMT/SMP roadmap. It repeatedly exercises the
complete owner-driven balancing lifecycle proven by Stage 21 instead of adding
a second scheduling path or a synthetic marker.

After the normal Stage 0–21 boot proofs, the kernel runs eight fresh stress
generations. Every generation creates eight managed workers on two overloaded
edge APs, lets the AP-local timer select parked least-loaded targets, migrates
live IRQ continuations, performs a real OrionGC stop-the-world collection, and
retires every worker back to the enrolled per-CPU idle contexts.

The next generation cannot begin until the previous generation has restored
the global thread registry and all native AP mailboxes. This catches stale
completion generations, leaked threads, lost timer continuations, queue-owner
violations, incomplete GC rendezvous and failure to restore idle ownership.

The Stage 22 runtime gate requires:

- nine successful balancing generations in total: the Stage 21 regression plus
  eight Stage 22 stress rounds;
- at least four migrations, sixteen preemptions and one observed managed
  continuation per worker in every generation; migrations are verified
  independently because a timer may legally move a worker before its first
  managed CPU sample;
- decisions from both overloaded edge APs and at least three distinct parked
  targets per generation;
- eight additional OrionGC/STW collections, each scanning all seven AP stacks;
- exact aggregate agreement between per-generation evidence and the final
  Stage 22 summary;
- registry and idle restoration after every round;
- QEMU `1S/4C/2T`, 1-vCPU regression, Cosmos 3.0.85 package/ISO builds and
  ARM64 compile regression, followed by a 60-second late-fault interval.

A single-CPU run executes the same generation loop as an explicit no-AP-work
regression and must report zero migrations, preemptions, resumes and remote GC
collections without changing scheduler state.

Stage 22 is complete only after the workflow passes for both 1 vCPU and the
required `1S/4C/2T` topology; the implementation checkpoint alone is not a
runtime claim.
