# SMT Stage 14 — managed AP residency across OrionGC

Date: 2026-09-18
Base: Stage 13 PR #63 (`24f1c29b7aa2b19a5690825ec0433db3adb49b84`)
Cosmos base: `v3.0.85` (`109ec2aacf2226b8cef53ab496920a285b626848`)
Branch: `smt/stage14-managed-ap-enrollment`

## Goal

Prove the runtime/GC prerequisite that was deliberately excluded from Stage
13: every application processor can remain inside managed C# while a real
OrionGC collection stops it through the native SMP rendezvous, resumes it, and
allows it to continue managed execution before returning to native idle.

This stage is intentionally narrower than managed scheduler-thread dispatch.
The AP entry is allocation-free, holds no managed heap references, does not
walk the scheduler object graph, and does not context-switch, migrate, balance,
or preempt a thread.

## Implementation

- Adds native command 7 and a cache-line-isolated Stage-14 mailbox for each AP.
- Enters a reverse-P/Invoke managed loop with interrupts enabled on every AP.
- Publishes deterministic per-AP heartbeats and checksums through native
  mailboxes without allocation, serial I/O, locks, or scheduler access.
- Runs one real `GarbageCollector.Collect()` on the BSP while all APs are in
  managed code. The existing vector `0xF3` stop-the-world handler must park and
  resume them.
- Requires every AP heartbeat to advance after the GC resume and then releases
  all APs back to the native HLT loop.
- Preserves the Stage 13 scheduler-state proof and all earlier SMP/SMT gates.

## Runtime evidence

The 8-vCPU (`1S/4C/2T`) gate requires this ordering:

```text
[SCHED-AP-RUNTIME] dispatch
[SCHED-AP-RUNTIME] resident aps=7
[GC-SMP] STOP epoch=N
[GC-SMP] RESUME epoch=N aps=7
[SCHED-AP-RUNTIME] gc-collection=N
[SCHED-AP-RUNTIME] cpu=1 heartbeats=... checksum=0x... state=returned-native-idle
...
[SCHED-AP-RUNTIME] cpu=7 heartbeats=... checksum=0x... state=returned-native-idle
[SCHED-AP-RUNTIME-TEST] PASS
```

The 1-vCPU regression performs the real collection without an SMP rendezvous
and requires `cpu=0 state=bsp-only`.

## Review boundary and next stage

Stage 14 proves managed AP residency across GC only. It does not make the AP
boot stack a registered managed thread stack, does not permit allocations or
managed references on an AP, and does not activate scheduler ticks there.

The next safe stage is AP idle-thread enrollment: bind each AP to a registered
idle execution context with explicit stack bounds and GC scanning rules, while
still avoiding runnable user threads and context switching. Preemption and
migration remain later, separately gated stages.
